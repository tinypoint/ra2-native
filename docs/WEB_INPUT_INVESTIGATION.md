# 两次触摸误框选：源码调查

2026-10-19。检查生产回退版本 3c02a0e 与撤回版本 ae4e797；没有启动游戏，没有发布新版本。以下区分代码事实与尚未复现的原因。

## 已确认的链路

1. v0.1.5 web/app.js 的 release 在普通 touch pointerup 中依次发送 MOVE、DOWN、UP，然后清空 active/touchPress。窗口捕获阶段监听 pointerup/pointercancel。因此源码并非根本没有发送 UP。
2. runtime/web/input.c 的 128 项队列按画面呈现推进，每轮最多一个按钮转换。runtime/web/screen.c 每至少 32ms 触发呈现；这不是游戏输入消费完成的通知。
3. USER32 hle_input_mouse 立即改全局光标和 g_keys，再将消息排入另一层队列。下一次呈现可能发生在 PeekMessage 的 pump 内。按呈现推进不能证明前一消息已被游戏处理。
4. 原游戏还有额外状态：sub_005233A0 在模式 0xA522AC 非零时写 0xA51FD0 的按键表；sub_005233D0/F0 在该模式读取此表，模式零才调用 GetKeyState/GetAsyncKeyState。因此仅观测 hle_lbutton_reads 或 g_keys 不足以证明游戏已经释放。
5. sub_00532A60 转换鼠标按钮消息，经 sub_005324D0 写入游戏自己的环形输入缓冲（对象 +0x114，读写索引 +0x314/+0x318）。按钮事件到达 USER32 仍不代表上层行为已执行。
6. sub_00522ED0 在部分模式读取 GetCursorPos，并将位置与消息分别处理。这使全局光标过早跳到下一触点成为需要核验的竞争路径。

## 另一个独立的丢事件风险

Web 入队失败返回 0，但 app.js 未检查返回值。队列满时可能丢 UP；USER32 的 1024 项队列满时也会丢最老消息。源码证明风险存在，但没有证据说明用户仅两次点击时发生过溢出，不能把它当成本次已确认根因。

## v0.1.6 菜单回归

hle_web_mouse_pending 扫描整个 USER32 鼠标队列，只要残留一条消息便永久停止推进下一次输入。next_message 支持窗口和消息范围筛选，不保证每条鼠标消息都会取走；所以这个等待没有可靠的完成条件。前端还有未经完整核验的 loading 阶段点击屏蔽。两者都不能重新投入生产。

## 修复与定位边界

应记录同一次点击在浏览器入队、USER32 出队/派发、游戏按钮状态更新的序号与坐标，且记录入队失败。用实际按钮处理完成作同步依据；不能只把整个队列清空或多等一次呈现视为完成。菜单保留正常消息处理，战场适配单独启用。任何等待有上限，不能因为消息筛选而锁死主菜单。

当前能定位到跨队列消费同步缺口，但未取得用户手机上失败点击的逐层轨迹，尚不能断言某一条 UP 丢失或晚到就是唯一原因。现有崩溃导出主要记录控件快照，不能回答这个问题。

## v0.1.7 修复实现（待手机验证）

- 撤销 v0.1.6 的场景桥接和 loading 点击拦截，界面恢复线上 v0.1.5 行为。
- MOVE 与随后的 DOWN 不再同一轮注入；相邻 MOVE 可连续处理，但遇到按钮边界停止。这让离散触点的位置先在释放状态下生效。
- 浏览器专用 USER32 副本在 DispatchMessage 的按钮窗口过程返回后增加完成计数；输入桥等待该计数变化再推进。仅等待按钮完成，不扫描全部消息。128ms 上限避免过滤消息、窗口消失或窗口过程需要后续输入时死锁。
- 队列容量增加到 1024，降低突发移动造成溢出的风险；这不是严格的无丢失保证。
- 不改原生 macOS 源码；未运行游戏交互测试。此变更解决已确认的时序缺口，手机上误框选是否彻底消失仍需用户验证。

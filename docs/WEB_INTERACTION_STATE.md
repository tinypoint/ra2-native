# Web 交互阶段识别研究

2026-10-19。仅分析现有源码、转换后的本机游戏代码和历史证据；未运行游戏验证，未改变线上交互或 macOS 代码。

## 结论

具备建立阶段桥接的源码落点，但现有 running 不能用于区分战场。优先从 Web 构建中的游戏循环边界发出阶段信号，并结合可见对话框进行输入路由；不要直接用帧数大于零或“没有下拉框”判定战场。

## 已找到的证据

- 逻辑帧全局 0xA40D2C 已由历史指令证据和性能采样核验，见 logs/game-frame-counter-evidence.json。0x540676..0x540684 读、递增和写回它。
- 转换后 recomp_0016.c 的 sub_00481BF0，在 0x481DBA 调用 sub_0053FBD0，在 0x481DC3 / 0x481DD1 调用 sub_0053F840，并通过 0x481DD8 回到循环；0x481DDA 开始后续清理。这是生命周期桥接候选边界，仍需覆盖读档、战役和异常退出路径。
- 不能将 sub_0053FBD0 的每次调用都视为进入战场：除上述循环，它还被 sub_006000D0 等多个位置调用。
- USER32 的 win_t 保存 kind、parent、owner、style、dlgproc、dlg_ended、seq 等。已有只读控件快照仅取部分字段，不能代表完整界面。
- USER32 run_modal 会禁用所有者窗口，运行对话框消息循环，退出时恢复所有者；create_dialog 可识别对话框生命周期，hle_dialog_hook 可提供资源 ID。可用于识别战场上的暂停、设置、存读档、确认退出等覆盖层，但具体资源 ID 尚未逐页映射。
- 0xA35DB1、0xA40C78、0x866250、0xA35DB0 均参与逻辑帧推进前的跳过条件，也在退出、结束处理等路径写入。尚未核验各自语义，不能给其中任意一个直接命名为暂停或战场标志。

## 建议实现

由 Web 专用构建改写生成副本，加入 menu / loading / battlefield 生命周期桥接；不修改共享原生源码。暂停和模态覆盖层单独建状态，不靠帧数停止增长识别。前端最后组合生命周期与交互覆盖层，决定启用哪些操作。

- 菜单和覆盖层：普通鼠标点击、移动、拖动；保留原游戏下拉框、滚动条行为；隐藏并释放视野摇杆、基地、取消。
- 加载或状态不明：不启用战场专属操作。不能因几百毫秒没有帧更新就判定加载。
- 战场且没有阻挡输入的覆盖层：启用战场控件和触摸适配。
- 任何阶段切换：先释放鼠标与方向键，清空未结束的触摸和输入队列，避免菜单点击跨到战场成为拖拽。
- 游戏内自绘对话框未必全走 USER32 模态循环，须核验；未知覆盖层默认不启用战场专属手势。

## 尚待验证

主菜单→遭遇战→地图加载→战场→暂停→恢复→退出回菜单，以及战役、读档、结算、联机路径。现有 Wasm 的内存布局地址需按程序 SHA 校验，新增 C 状态桥接会改变程序包，不能沿用未经核验的地址。此研究没有宣称这些路径已被运行验证，也没有发布启发式分类器。
